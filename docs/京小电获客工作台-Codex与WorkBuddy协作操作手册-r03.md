### 5.1 准备

1. 在 Codex 中打开明确的工作根目录；验收候选时使用隔离测试项目，不能把正式客户目录当作临时夹具。

3. 先在新会话确认候选工具实际出现，再调用 `get_capabilities`。只修改配置文件或让 `codex mcp list` 显示服务名，不等于本会话已经发现工具。
4. WorkBuddy 保留独立兼容检查；旧版原生发现未通过，不得用它的历史备用回执代替 Codex 验收。

MCP 是助手调用工作台受限功能的接口。它只允许规定的查询和建议提交，不赋予发送客户消息、批准报价或随意改库的能力。

### 5.2 每次开工

让 Codex 业务会话先调用 `get_capabilities`，再调用 `get_today_queue`。检查返回中的 `ok`、`error`、版本和能力字段。

本版本 `send_messages`、`live_receiver`、`auto_receive` 应为 `false`。如果返回不同，停止按旧手册推断，先核对实际版本和变更来源。

网页 `serve` 的 `--data-dir`/`--approved-data-dir`、原生 MCP 的 `JXD_DATA_DIR`/`JXD_APPROVED_DATA_DIR` 和备用脚本父进程的同名变量必须成对一致；实际目录须等于本人批准的绝对路径，并由维护者先用这两项显式运行 `migrate`。脚本只把这两个变量传给子 MCP；SDK 默认环境不会自动继承。缺失、空白、相对路径、实际与批准值不一致均拒绝，未初始化或迁移头不符也会停止。切换时由维护者逐入口核准，不在 JSON 中新增数据目录键，也不转传整个环境。

### 5.4 怎样判断成功

- 查询：必须 `ok=true`，并拿到对应 `data`。空列表是“本次无记录”，不是连接失败。
- 写入：必须 `ok=true`，检查真实记录 ID，再在网页对应页面核对。
- 报错：保留 `error.code`、说明及 `retryable`；不得把“工具执行完毕”写成“业务保存成功”。
- 支持 `request_id` 的写入重试必须沿用原编号和原内容；不要用换编号的方式盲目重做。
- 分页默认 20 条、最多 100 条；机会历史默认 10 条。没有翻页不能声称已读全部历史。

## 8. 一次完整的主动获客流程

### A. 创建研究

在“获客任务”明确填写本次地区、采购场景和目标候选数，再点击“创建任务”。地区和场景无预填值；目标默认 10 条、单批最多 30 条。历史测试任务不构成正式范围。

点击该任务的“复制获客任务指令”，粘贴到已加载本工作台 MCP 的 Codex 业务会话。明确要求执行这个已有任务，不重复创建。也可由你直接授权 Codex 创建单次任务；两种入口选一种即可。

### B. 检索与回写

Codex 先读取 get_capabilities，再只用实际 `task_id` 读取任务并检索，优先使用本次场景相关机构的官网、公开项目原件和采购公告。候选按十项核对：公司全名、具体项目、地区、地址证据、来源 URL、公开单位电话、发现日期、原文摘要、匹配理由、未知项。公开单位电话和未知项可留空；电话须有公开机构来源，不猜测个人号码。0.5.0 另有两项可选：`source_channel` 只能取 `get_capabilities.source_channels` 中本人维护的值，不确定就留空；招标类公告写明投标截止日时填 `bid_deadline`，不得早于 `published_at`，截止 7 天内的候选和机会会进入今日队列（kind=`bid_deadline`）。

发布主体、发布日期、项目状态能核实才填。公司注册地址和招标代理地址不能当作项目位置；历史中标、项目开工或行业身份不能当作当前采购意向。

公开招标发布的采购项目只收执行当日及此前 6 个北京时间日发布的原公告，含首尾日期。必须记录公告原文发布日期 `published_at`；只看到转载日期、日期不明或超期的公告不录为新候选，在任务回执 `note` 写明跳过数量和来源。其他官网或项目资料不套用招标公告的七日时限。

资料不足或时间未到时，你可把候选设为“暂缓观察”，填写原因类型和复核日期；到期会回今日队列。继续核实时填写依据，候选 ID 不变，复核记录保留。来源核验可逐条保存独立 URL 和本来源支持的事实；冲突来源不会自动覆盖原来源。同一 URL 与事实主张后续经本人核清后，统计采用最新核验结论，历史冲突仍留痕。需求确认统计读取项目和非历史采购机会中由本人确认的需求卡。效果统计按近 30 天同一时间窗显示每项分子、分母；分母为零时显示“暂无数据”。

经 `submit_candidates` 回写后，报告真实新增、重复、失败和任务 ID。部分失败记 partial，全失败记 failed；没有结果也如实说明，不以模拟数据凑数。

### C. 人工审核候选

在“线索池”打开项目名并核对来源，分别判断：客群匹配、需求证据、采购角色、采购时间、证据可信程度、推进优先级。

| 发现 | 合理处理 |
|---|---|
| 项目在目标区域，尚无采购证据 | 保留需求未知，安排核实 |
| 有维修问题，但采购未定 | 记录问题原文，不升级为确定需求 |
| 对接人角色不清楚 | 角色未知，补核实职责与权限 |
| 来源打不开，只看到搜索摘要 | 标待核对，不能标“原文已核对” |
| 不符合本批地区/场景 | 说明原因，排除或留待另批，不擅自扩大任务 |

核对后由你接受建档。建档是建立待核实项目，并不意味着客户已经确认购买。

### D. 联系与需求核实

你使用已核实的合法联系渠道自行联系。AI 可准备开场草稿，但不猜测手机号、微信号或采购权限。

围绕具体采购机会核实：联系人职责、采购权限、产品或设备规格/数量与现状、实际需求和预计采购时间。每次只问最必要的 1—2 个问题；预算未知就保留未知。

### E. 采购推进

在“客户与项目”中进入对应项目，选择或新建本次采购机会。首购、补货、改造分别管理，避免沿用错误历史。

本次采购阶段包括：待核实、确认需求、报价或试样、采购、补货跟进、暂缓、关闭。由你依据事实确认；AI 只能建议。

## 9. 沟通、报价、试样与回访

### 记录一次真实沟通

进入采购机会的“沟通与下一步”，填写实际沟通记录、结果、耗时、下一步动作和到期日期。未知耗时留空；下一步和日期成对填写。

也可以把真实沟通提供给 Codex 业务会话，让它调用 `propose_opportunity_update`，一次提出摘要、阶段、标签与下一步建议。到“审核中心”核对并修改，再由你点击“我已核实，确认以上变更”。

若一个项目存在多个机会，必须指定 `opportunity_id`；收到 `AMBIGUOUS_OPPORTUNITY` 时由你选择，不默认用最新机会。

### 正式报价和样品

在采购机会中的“本次报价与试样”展开“新增报价 / 试样”，由你确定类型、型号、数量、金额及回访日期。未知金额留空，不用 0 代表未知。

AI 只准备材料，报价、交期、质保及节能效果必须有适用依据并由你确定。先核实本次需求，再按页面约束推进；被拦截时补齐事实，不绕过限制。

报价后的默认建议是 2 天回访，样品确认收到后默认建议 3 天回访；客户约定与当前设置优先。寄出不等于收到，未知签收日期不能推定。

记录“已采购”沟通结果不会自动修改采购阶段；实际完成采购后还需由你确认阶段。待办未实际完成时，使用“改期”并写原因，不点击“完成”掩盖逾期。

## 10. 处理抖音/企微咨询

### 录入真实咨询

当前从你能正常访问的渠道获取真实原文，在“咨询收件箱”展开“录入真实咨询”，填写平台、接收账号 ID、事件类型、带时区发生时间和原文；消息/评论 ID、用户 ID、视频 ID、昵称及链接按真实掌握情况填写。0.5.0 可选填来源渠道 `source_channel`，只能取设置页维护的渠道，不确定就留空。

时间示例格式：`2026-11-09T10:00:00+08:00`，示例不代表实际发生时间。没有可靠平台 ID 时不要编造；按真实手工来源处理并说明去重限制。

公司、项目、城市可以未知，不能把昵称当成企业身份。批量处理使用收件箱内的专用导入模板，先预览，再确认有效行。

### 结构化字段待审

对于已经录入的真实咨询，Codex 业务会话可用 `propose_inquiry_fields` 提出公司、项目名、地区、具体场景、产品或设备规格与数量、主要问题、预计时间、年照明电费区间八项中的有依据内容（电费区间只能为 `≥30万`、`5–30万`、`<5万`、`未知`），并附客户原话依据。底层字段名 `lamps` 为兼容旧 MCP 契约而保留，不代表正式业务范围。未知项省略。建议进入审核中心和咨询页；你对照原话逐项修改、确认后才写入正式咨询。该工具不能改处理状态、采购意向或采购机会，也不会自动建档、回复或发送。重复调用要沿用同一 `request_id` 和相同内容。

### 拟回复、审核与发送

1. 让 Codex 业务会话读取 `list_inquiries` 和目标 `get_inquiry_context`。
2. 先回答客户已问的问题，再补 1—2 个必要问题；请求照片/数据时说明用途。
3. 经 `propose_inquiry_reply` 保存待审草稿。
4. 你从审核中心进入关联咨询，核对原话、编辑并确认回复。
5. 由你复制到原渠道发送。批准或复制均不等于已发送；真实发送及反馈另行记录。

客户可以继续留在抖音，也可以自愿转企微。互关不是当前流程的硬条件；抖音昵称不能证明微信身份。手工录入成功不等于平台自动接入成功。

## 11. 审核、停联与业务知识

### 审核清单

批准前核对对象 ID、原话、来源、时间、本次机会、未知项、报价/政策依据、下一步和日期。发现判断错误，可在关联候选或机会保存本人判断，再拒绝旧建议；避免让冲突建议继续留待执行。

### 客户明确拒绝联系

立即停止继续触达文案。通过 `request_suppression` 提交明确拒绝原话、来源、带时区时间，以及唯一明确目标的 project_id、contact_id 或 inquiry_id。

只有咨询具备完整 platform/account_id/user_id、拒绝原话是原文中的明确拒绝句式且时间一致时，系统才返回 `match=stable`、`paused=true`，并即时暂停该稳定身份范围内的咨询。普通子串、否定或双重否定、条件分支、第三人引用、疑问、改道联系对象、项目/联系人目标、身份缺失或时间不一致均返回 `match=weak`、`paused=false`，只进入待审队列，当前不会自动停联。

在审核中心核对原话、对象和范围后，本人对弱匹配确认停联或对已暂停事项确认保持停联；确认前系统会复核停联效果仍存在。助手无解除权限。误匹配只能由本人核实证据后撤回；同一平台用户若有后续独立停联，早期事件纠错会被拒绝，不能删除仍有效的共享停联。已经取消的待办和草稿不会自动恢复。不得重新导入、换联系方式写法或换来源来绕过停联。没有稳定用户 ID 时，不能凭同名扩大停联范围。

### QA 和政策使用

业务问答 r19 是历史快照，现行主写入口为 JXD-KB-001。使用某条话术前，在现行知识库按编号核对版本、批准情况、适用业务模式和具体合同；直采与 EMC 不混用，不把整套资料一概标为待审或已批准。

CONF-20261104-16 / [现行 POL-14](/Users/dkai2024163.com/ai/product/jingxiaodian-knowledge/kb/policies/POL-14.md) 已记录十年正常期满的设备、账号与数据归客户。移交安排、提前终止及后续运维等仍有待确认项；不再写“所有权待合并”，也不把期满条款套用于提前终止。云端发布及工作台自动同步仍分别验收。

真实节电率、现售价格、服务资源与履约承诺不能从旧话术外推。知识文件同步尚未自动化，不能假定执行助手已获得最新政策。
